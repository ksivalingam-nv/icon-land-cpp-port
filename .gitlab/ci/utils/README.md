# General information

This directory contains a collection of common building blocks (*templates*) for ICON GitLab CI jobs. They are implemented as [hidden jobs](https://docs.gitlab.com/ci/jobs/#hide-a-job), which can be [extended](https://docs.gitlab.com/ci/yaml/#extends) and [referenced](https://docs.gitlab.com/ci/yaml/yaml_optimization/#reference-tags) by the normal ones. However, the templates in this directory are merely snippets, which are not guaranteed to be usable out-of-the-box (i.e. a normal job that implements a [`script`](https://docs.gitlab.com/ci/yaml/#script) and only `extends` a hidden job implemented in this directory is not necessarily valid). It is also possible that some templates require the others.

# Requirements and conventions

1. Names of all jobs defined in `.gitlab/ci/utils/<filename>.yml` (i.e. in this directory) must be `.utils:<filename>` or start with `.utils:<filename>:`. This makes it easy to find the file with the definition by the job name.
2. The jobs are not allowed to specify any [job keywords](https://docs.gitlab.com/ci/yaml/#job-keywords) properties except for:
    - [`artifacts`](https://docs.gitlab.com/ci/yaml/#artifacts);
    - [`before_script`](https://docs.gitlab.com/ci/yaml/#before_script);
    - [`cache`](https://docs.gitlab.com/ci/yaml/#cache);
    - [`extends`](https://docs.gitlab.com/ci/yaml/#extends);
    - [`variables`](https://docs.gitlab.com/ci/yaml/#job-variables).
    Exceptions to this rule are possible but must be discussed during the review.
3. It is preferable to write the [`before_script`](https://docs.gitlab.com/ci/yaml/#before_script) as a single multi-line string implementing the required logic in a subshell:
    ```yaml
    .utils:whatever:job:
      before_script:
        - |
          # !reference[.utils:whatever:job, before_script]
          (
            whatever_var='whatever value'
            set -ux
            whatever_cmd "${whatever_var}"
          ) 2>&1
    ```
    The benefits of this approach (see the snippet above):
      - the `whatever_var` shell variable does not leak to the scripts run by the jobs that extend `.utils:whatever:job`;
      - the log of the job is more informative: `whatever_cmd "${whatever_var}"` line generated by GitLab vs. `+ whatever_cmd 'whatever value'` generated by the shell (see `set -x`);
      - `set -u` makes the script more robust, but the subshell does not let it leak to the rest of the script (note that GitLab runners normally run `set -eo pipefail` before running the job scripts);
      - the comment on the first line results in the `$ # !reference [.utils:whatever:job, before_script] # collapsed multi-line command` message in the log, which makes it easy to find the respective code;
      - the `2>&1` stream redirection ensures that the shell trace and the output of the respective command are not mixed in the log (GitLab collects the standard output and error streams separately and can emit them in the mixed order).
4. The [`cache:key`s](https://docs.gitlab.com/ci/yaml/#cachekey) must not be hard-coded. They should at least contain the [`${CI_JOB_NAME_SLUG}`](https://docs.gitlab.com/ci/variables/predefined_variables/#predefined-variables) substring.
5. Jobs can extend only jobs defined in this directory. If the [`include`](https://docs.gitlab.com/ci/yaml/#include) keyword is required, it must be specified at the top (after the license header) of the YAML file.
6. Names of all custom [`variables`](https://docs.gitlab.com/ci/yaml/#job-variables) defined by a job must start with `ICON_CI_UTILS_<FILENAME>_`. The `ICON_` prefix tells that it is a custom variable, which is not supposed to affect any tools run by the job. The `CI_` infix tells that the variable is CI-specific and is supposed to affect neither ICON scripts nor ICON itself. The `UTILS_<FILENAME>_` infix makes it easy to find the file with the definition of the job by the variable name.
