# ICON-Land C++ function and module porting backlog

Date: 14 October 2026  
Status: Proposed work packages; no skeleton, capture mode or function ports were implemented for this document.  
Scope: The current reduced standalone `jsbach_lite` application.

This is a separate companion to [the OO design and test plan](https://github.com/ksivalingam-nv/icon-land-cpp-port/blob/main/ICON_LAND_CPP_DESIGN_AND_TEST_PLAN.md). That document is unchanged. This backlog names actual Fortran routines/modules, proposes their C++ responsibilities, specifies planning prerequisites, and assigns a comparison gate to each increment.

The inspected source is the public snapshot at `6a4d5fec6820dc8054d81b4e7e97f37440c19044`. Source links are pinned to that commit. Existing routine names and line locations were checked against the checkout and source-derived call graph. Dependencies below are proposed engineering prerequisites, not a compiler-resolved graph of every Fortran call or an estimate of effort.

## 1. Entry gates and how to use this backlog

The skeleton is a future entry gate, not something already built in this chat:

- **S0 - bootstrap established:** C++ entry point, build path, MPI lifetime, master namelist/configuration, host-component count/assignment, deterministic capture output and clean exit. Exact startup fixtures pass with 1, 2 and 4 ranks. Application main does not yet claim to run land physics.
- **R0 - reference harness established:** fixed source/toolchain/input manifests, native-precision capture schema, validated original Fortran reference, fresh-process case runner, structural/numerical comparator, timeout/failure reporting and reviewed policy.
- **FX - fixture available:** an immutable captured input/output case for the particular responsibility, including configuration and required parameters. FX permits offline component work; it is not a substitute for implementing native input or initialisation.

Each package has three completion states: **contract defined**, **component comparison passed**, and **native integration passed**. A fixture-backed implementation can reach the second state while native services remain pending. A recording callback, interface declaration or stub does not constitute a scientific implementation.

A package containing several named helpers must be split into one small implementation/review change per helper where practical. Constructors, simple related getters and enum mappings may share one change. Large routines such as `new_model_config`, `jsbach_init`, `get_data_and_update_field`, `soilhyd`, and `jsbach_model` must be split by responsibility rather than copied wholesale.

Before implementing a package:

1. Inspect the exact routine body and active preprocessor/configuration paths.
2. Record required inputs, changed state, units, bounds, aliases and error behavior.
3. Resolve its called-helper/data closure. Add newly discovered required helpers to the package contract or a separate prerequisite.
4. Select independent reference fixtures and at least one hand-checked invariant/expected-result test.
5. Implement the C++ responsibility and run its comparison gate before connecting it to the growing application.
6. Verify the next integrated checkpoint using actual state and services; report adapter-backed or unsupported paths explicitly.

Use the prerequisite IDs to choose ready work. Tables are organised by responsibility, so an earlier table can legitimately depend on a helper in a later table. The reviewed prerequisite graph is acyclic; native data/call closures still require inspection per package.

## 6. Capture and comparison rules for every package

Extend the Fortran and C++ capture schema together. Default capture remains off. For startup, stop after `master_control_ready`; for tasks, capture at the task boundary and stop only at a safe completed timestep/lifecycle boundary. Coordinate all MPI roles and finish outstanding work before shutdown.

Record configuration plus raw/native-precision inputs and outputs. Metadata identifies case, model, timestep, tile, process, task occurrence, action, logical axes, global cell IDs, bounds, dtype, units and masks. Across decompositions, align scientific fields by global cell identity and compare ownership/halo mappings separately. Compare communicator memberships, not raw handles.

Use exact comparisons for structure/configuration and fixed-toolchain infrastructure fields. For numerical routines/backend changes, use the reviewed per-field/per-test policy from the main design document. For finite unmasked values, a proposed tolerance gate is:

```text
abs(candidate - reference) <= atol[field] + rtol[field] * abs(reference)
```

Report first divergent event, maximum absolute/scaled relative error, RMS error, failing-element count, ULP diagnostics where applicable and worst cell/tile/level/date. Check masks, precision, coordinates and unexpected non-finite values first. Do not pass by comparing only averages, a subset of available fields, or rounded public output.

For every package also check one invariant or hand-computed expected case independent of Fortran. Run reference and candidate from independent copies of state in fresh processes. Keep instrumented and uninstrumented application regressions; do not silently replace old fixtures or broaden thresholds after a failure.

## 8. Completion checklist and first divergence response

A package is ready for native replacement when:

- Its exact source behavior and used-helper closure are recorded.
- Its C++ responsibility and ownership are defined without recreating hidden globals.
- Required defaults, conditional branches, error cases and metadata are covered by admitted cases.
- Reference/candidate manifests contain all required events and fields.
- Unit/invariant and differential gates pass with immutable reference inputs.
- The next relevant application checkpoint passes using real services/state rather than a successful stub.
- Unsupported, fixture-backed and Fortran-adapter-backed behavior is listed explicitly.

On a mismatch, find the first differing checkpoint, replay that package with the captured pre-state, check units/layout/index/aliasing and operation order, then investigate arithmetic or backend effects. Fix and rerun the affected gates. Reference and tolerance changes require explicit review.

Final C++ completeness is a used-call/data closure gate over the selected retained application, not a count of translated functions. All required callbacks, parameter initialisation, host numerical helpers, state time levels, diagnostics, I/O, restart and runtime services must be accounted for. Audit every linked dependency, including mtime/CDI/MemMan/iconmath/Fortran support, and the build configuration itself.

The original Fortran experiment requires external grid/forcing/initial datasets referenced under Levante's `/pool/data`; dependency submodules are pinned but not populated in this checkout. Fresh baselines, runtime access and compiler/backend choices are prerequisites for executing the plan. Source inspection alone does not establish numerical pass results.
